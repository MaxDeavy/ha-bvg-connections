# Contributing

Thanks for helping with BVG Verbindungen. This file covers the development setup, the commit message format and how releases and the changelog are made. User documentation lives in the [README](README.md); custom-repository and zip installs are in [docs/MANUAL_INSTALL.md](docs/MANUAL_INSTALL.md).

## Development setup

```bash
# Python (Home Assistant 2026.10 needs Python 3.14)
pip install -r requirements_test.txt
ruff check . && ruff format --check . && pytest

# Card
cd frontend && npm ci && npm run typecheck && npm test && npm run build   # writes custom_components/bvg_connections/frontend/
```

The built card bundle is committed. CI fails if `npm run build` changes it, so rebuild and commit it together with every change under `frontend/src/`.

### Local test data

Personal stops and addresses **never** go into the repository, not even in tests, screenshots or commit messages. Use neutral, well-known stops (for example S+U Alexanderplatz or S+U Hauptbahnhof) in anything you commit.

For your own data, copy `local_defaults.example.yaml` to `local_defaults.yaml` (gitignored) and enter your connections there. Then:

```bash
./scripts/dev_ha.sh                    # starts HA in .dev/config with this integration
python scripts/dev_seed.py --dashboard # creates the entries through the real config flows
```

The seed script onboards a fresh instance with the user `dev` / `dev-password` (override with `HA_USERNAME` / `HA_PASSWORD`) and creates the dashboard `/bvg-connections`.

The line colours (`line_colors.py`) are generated by `scripts/gen_line_colors.py` from the VBB GTFS feed. The feed only has colours for S-Bahn and U-Bahn; tram, bus, ferry and regional trains use product colours.

## Commit messages

Commit subjects follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). The changelog is generated from them, and the `Commits` workflow checks every pull request and every push to `main`.

```text
type(scope)!: description
```

- `scope` is optional, lowercase (`a-z`, `0-9`, `_ . / -`), for example `card`, `config_flow`, `api`.
- `!` marks a breaking change; it shows up as **BREAKING** in the changelog.
- Write the description in English, imperative mood, without a trailing period: `fix(card): show the platform change on transfers`.

| Type | Changelog section |
| --- | --- |
| `feat` | Neu / Added |
| `fix` | Behoben / Fixed |
| `fix(security)` | Sicherheit / Security |
| `perf`, `refactor` | Geändert / Changed |
| `revert` | Entfernt / Removed |
| `docs` | Dokumentation / Docs |
| `test`, `build`, `ci`, `chore`, `style` | not listed |

Merge and revert commits generated by git are accepted as they are. Check a range locally with:

```bash
python scripts/check_commits.py origin/main..HEAD
```

## Changelog

`CHANGELOG.md` is only written locally, never by a bot. New release sections are inserted below the `<!-- next-release -->` marker by `scripts/release.py`, which runs [git-cliff](https://git-cliff.org) with `cliff.toml`. You can edit the generated text before committing; older sections are not regenerated.

```bash
pip install git-cliff

python scripts/release.py preview   # what the next release section would contain
# same as: git-cliff --config cliff.toml --unreleased --strip all
```

## Releasing

Versions follow [Semantic Versioning](https://semver.org). Releases are cut by the maintainer from an up-to-date, clean `main`:

1. Make sure CI is green on `main` and check the upcoming section:

   ```bash
   git switch main && git pull
   python scripts/release.py preview
   ```

2. Prepare the release (example `0.1.2`):

   ```bash
   python scripts/release.py prepare 0.1.2
   ```

   This inserts the changelog section, sets the version in `manifest.json`, `const.py`, `pyproject.toml`, `frontend/package.json`, `frontend/package-lock.json` and `frontend/src/card.ts`, rebuilds the card, and creates the commit `chore(release): 0.1.2` plus the annotated tag `v0.1.2` with your own git identity. Nothing is pushed.

3. Review the commit (`git show`), amend the changelog wording if needed (then move the tag with `git tag -fa v0.1.2`), and push:

   ```bash
   git push origin main v0.1.2
   ```

4. The `Release notes` workflow checks that the tag matches the manifest version and shows the notes in its run summary (also as the `release-notes` artifact). It does **not** publish anything.

5. Publish the GitHub release yourself, so it appears under your account:

   ```bash
   python scripts/release.py notes 0.1.2 > /tmp/notes.md
   gh release create v0.1.2 --title v0.1.2 --notes-file /tmp/notes.md
   ```

   Or on GitHub: *Releases → Draft a new release*, pick the tag `v0.1.2` and paste the notes. HACS offers the update once the release is published.
